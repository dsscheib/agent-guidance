# Documentation, authority and decisions

Kind: Policy. It applies as written; changing it needs an owner decision.

## One authoritative home
The routing table in [AGENTS.md](../AGENTS.md) is the single map of which document owns which subject, and which documents a change must update. When a user authorizes a decision, update the owning document so later agents can apply the adopted rule. Keep examples, proposals, inspected implementation and executed evidence distinct.

Each rule has one home. AGENTS.md may summarize a rule in one line with a link to that home. Other documents link to the home instead of restating the rule, so the copies cannot drift apart.

Authority is assigned by subject. Technical design must implement domain, UX and security contracts. Code establishes what exists, not permission to change requirements. When references conflict, record:
- the competing references,
- the inspected behavior,
- the impact,
- a proposed resolution,
- the owner decision required.

Preserve current behavior while the conflict is unresolved. Never weaken security to hide an implementation gap.

## Document kinds
Every packaged file declares a kind in `PACKAGE_MANIFEST.json` and in its opening line:

| Kind | Meaning | Who edits |
|---|---|---|
| Entry / adapter | Agent entry points and generated tool wrappers | Adapters are generated by `check_package.py --sync-adapters`; never hand-edit them |
| Policy | Rules that apply as written | Changed only by an owner decision |
| Template | Structure to fill in with project values | Filled during bootstrap and as work proceeds |
| Register | Live records that start empty | Appended by agents and people as work happens |
| Procedure | Step-by-step workflows, exposed as agent skills | Changed like policy |
| Profile | Optional stack or tier rules | Binding only once adopted in PROJECT_PROFILE.md |
| Guardrail | Tool permission files that mechanically enforce AGENTS.md rules | Aligned with the adopted git policy; see [AGENT_TOOLS.md](AGENT_TOOLS.md) |
| Tooling | Checker and hooks | Changed like policy |

## Status and completion
This section is the home of the status vocabulary and the three completion states.
- **Proposed:** awaits a decision; no implementation authorization.
- **Accepted requirement:** supported by a decision or reference; no implementation claim.
- **Implemented/inspected:** source revision and inspection date; no test claim.
- **Verified:** records the executed check, result, environment, candidate, date, operator and evidence.
- **Blocked/failed/not verified/in progress:** records an explicit reason and the next action.
- **Accepted exception:** records the specific scope, authority, review or expiry date and remediation. It keeps the failed or unverified gate disposition.

Report three states independently:
1. **Implementation complete:** the authorized scope is delivered and reviewed.
2. **Verification complete:** current passing evidence exists for all applicable checks.
3. **Release accepted:** the final audit and required gates are done, and an authorized decision has accepted the identified candidate and environment.

A scoped documentation check can pass without accepting an application release. None of these states authorizes deployment.

## Registers and history
[OPEN_WORK.md](OPEN_WORK.md) is the single current register. Each entry has a stable ID, status, owner, impact, next action and closure evidence. Keep closed entries. Reviews and archived plans are advisory or historical, not alternate live registers. Never fabricate signatures, owner approval or consent, and never infer them from generated acknowledgment fields.

## Useful documentation
- Document setup, build, test and operations commands only after inspecting them, and label illustrative commands and planned files explicitly.
- Maintain configuration names, defaults, units, precedence, secret locations and restart requirements.
- Date time-sensitive support claims and cite primary evidence in [SOURCES.md](SOURCES.md).

Update only the documents the change affects, as listed in the routing table. Record durable architecture and dependency tradeoffs with [decisions/ADR_TEMPLATE.md](decisions/ADR_TEMPLATE.md); routine helpers need no ADR.

Release records include the candidate, schema and configuration, executed checks, known limitations, upgrade and recovery steps, and evidence. Before delivery, review links, examples, code fences, secret exposure and consistency. Correct documentation drift without concealing defects. Use clearly synthetic placeholders, never plausible real credentials.
