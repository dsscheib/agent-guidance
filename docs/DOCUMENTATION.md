# Documentation, authority and decisions

Kind: Policy. It applies as written; changing it needs an owner decision.

## One authoritative home
The routing table in [AGENTS.md](../AGENTS.md) is the single map of which document owns which subject, and which documents a change must update. When a user authorizes a decision, update the owning document so later agents can apply the adopted rule. Keep examples, proposals, inspected implementation and executed evidence distinct.

Each rule has one home. AGENTS.md may summarize a rule in one line with a link to that home. Other documents link to the home instead of restating the rule, so the copies cannot drift apart.

Authority is assigned by subject. Technical design must implement domain, UX and security contracts. Code establishes what exists, not permission to change requirements. When references conflict, record:
- the competing references,
- the inspected behavior,
- the impact,
- a proposed resolution,
- the owner decision required.

Preserve current behavior while the conflict is unresolved. Never weaken security to hide an implementation gap.

## Document kinds
Every packaged file declares a kind in `PACKAGE_MANIFEST.json` and in its opening line:

| Kind | Meaning | Who edits |
|---|---|---|
| Entry / adapter | Agent entry points and generated tool wrappers | Adapters are generated by `check_package.py --sync-adapters`; never hand-edit them |
| Policy | Rules that apply as written | Changed only by an owner decision |
| Template | Structure to fill in with project values | Filled during bootstrap or by owner decision. A change adds only the rows it creates, such as its own route or requirement; it never fills sections the project has not configured |
| Register | Live records that start empty | Appended by agents and people as work happens |
| Procedure | Step-by-step workflows, exposed as agent skills | Changed like policy |
| Profile | Optional stack or tier rules | Binding only once adopted in PROJECT_PROFILE.md |
| Guardrail | Tool permission files that mechanically enforce AGENTS.md rules | Aligned with the adopted git policy; see [AGENT_TOOLS.md](AGENT_TOOLS.md) |
| Tooling | Checker and hooks | Changed like policy |

## Status and completion
This section is the home of the status vocabulary and the three completion states.
- **Proposed:** awaits a decision; no implementation authorization.
- **Accepted requirement:** supported by a decision or reference; no implementation claim.
- **Implemented/inspected:** source revision and inspection date; no test claim.
- **Verified:** records the executed check, result, environment, candidate, date, operator and evidence.
- **Blocked/failed/not verified/in progress:** records an explicit reason and the next action.
- **Accepted exception:** records the specific scope, authority, review or expiry date and remediation. It keeps the failed or unverified gate disposition.

Three completion states are kept separate:
1. **Implementation complete:** the authorized scope is delivered and reviewed.
2. **Verification complete:** every applicable gate has current passing evidence. For a change, this means `python3 check_package.py --verify` printed `Verification: complete`. The agent quotes that line and never writes its own verification status; a gap or failure it lists is reported as such.
3. **Release accepted:** the final audit and required gates are done, and an authorized decision has accepted the identified candidate and environment.

A scoped documentation check can pass without accepting an application release. None of these states authorizes deployment.

A routine change report gives implementation (done, partial or not started) and the quoted `Verification:` line. Report all three states only for a release, or when the owner asks whether work is done. Do not repeat them, or lists of actions that did not happen ("no commit, push or reset occurred"), in documents. A document records what is true and what happened.

## Registers and history
[OPEN_WORK.md](OPEN_WORK.md) is the single current register. Each entry has a stable ID, status, owner, impact, next action and closure evidence. Update entries in place. When an entry closes, shorten it to one row with its closure evidence; remove closed rows once a release note or merged pull request records them, because git keeps the history. Reviews and archived plans are advisory or historical, not alternate live registers.

[RELEASE_NOTES.md](RELEASE_NOTES.md) holds one short entry per release or review deployment. It is the only place dated delivery history goes. Never fabricate signatures, owner approval or consent, and never infer them from generated acknowledgment fields.

## Useful documentation
- Document setup, build, test and operations commands only after inspecting them, and label illustrative commands and planned files explicitly.
- Maintain configuration names, defaults, units, precedence, secret locations and restart requirements.
- Date time-sensitive support claims and cite primary evidence in [SOURCES.md](SOURCES.md).

Update only the documents the change affects, as listed in the routing table. Record durable architecture and dependency tradeoffs with [decisions/ADR_TEMPLATE.md](decisions/ADR_TEMPLATE.md); routine helpers need no ADR.

## Document budget
This section is the home of AGENTS.md rule 16. Documents describe the current state. Git, pull requests and RELEASE_NOTES describe how it got there.

| Document | Holds | Never holds | Limit checked by `check_package.py` |
|---|---|---|---|
| PROJECT_PROFILE.md | Stable facts: identity, tier, stack, commands, policies | Dated status, deployment or authorization sections | 250 lines; no headings that contain a date |
| OPEN_WORK.md | Current status and open items, overwritten as they change | "Previous checkpoint" narratives | 150 lines |
| RELEASE_NOTES.md | One entry per release or review deployment, at most about 5 lines each | Raw logs, full command transcripts | None |
| VERIFICATION_MATRIX.md | One row per requirement, updated in place with the latest evidence | A row per run | None |
| README, DESIGN_DOC, ROADMAP | Product description, setup and usage, requirements, planned scope | Current status; they link to OPEN_WORK instead | None |

- **No report file per change.** The delivery report goes in chat or the pull request description. Write a separate verification document only for a release record or when the owner asks for one.
- **Keep bulky evidence out of the repository.** Logs, traces, screenshots and test-result folders stay in CI artifacts or ignored local paths. Reference them by path or run, and commit only what a release record needs.
- **Tool instruction files only point to AGENTS.md.** A `GEMINI.md` or `.github/copilot-instructions.md` that holds rules of its own is flagged by the checker; move its rules to their routed home ([AGENT_TOOLS.md](AGENT_TOOLS.md)).
- **Over a limit?** Move history to RELEASE_NOTES or delete it, rather than raising the limit. Raising a limit is an owner decision recorded in PROJECT_PROFILE.md.

## Writing style
Agents copy the style of what they read, so write the way you want reports written.
- Lead with the answer or the current state.
- Use short, plain sentences, one idea each. Prefer a list or table over a sentence packed with commas and slashes.
- Name things the way the user does. Define a term the first time it appears.
- Say what is true and what happened. Do not pad with disclaimers or restate the same caveat in every section.
- Prefer links over repeating content.
- Do not explain a status line or list what you did not do. The reader acts on what changed and on what needs them.

## Release records
Release records include the candidate, schema and configuration, executed checks, known limitations, upgrade and recovery steps, and evidence. Before delivery, review links, examples, code fences, secret exposure and consistency. Correct documentation drift without concealing defects. Use clearly synthetic placeholders, never plausible real credentials.
