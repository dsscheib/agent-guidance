# Maintaining the guidance package

This file exists only in the template repository and is never installed into projects. Its presence switches `check_package.py` to template mode, and it tells agents (AGENTS.md, first paragraph) that they are editing the package rather than working in a project.

## Rules for editing the package
1. **Templates stay empty.** Registers (`docs/OPEN_WORK.md`, `docs/VERIFICATION_MATRIX.md`, `docs/PRODUCTION_READINESS.md`, `docs/ROADMAP.md`, `docs/SOURCES.md`) contain only placeholder rows. Record package history in the log below, never in a shipped file. The checker rejects dated entries in registers.
2. **One home per rule.** Before adding a sentence, find the rule's home through the routing table in AGENTS.md and the status section of `docs/DOCUMENTATION.md`. Link to it instead of restating it.
3. **Keep AGENTS.md small and concrete.** Write each rule as a rule, a reason and an example. Move detail into routed documents or procedures. Target size: under about 10 KB for the largest installed project (Enterprise with every feature). Its routing and procedure tables are generated: edit the module-tagged rows under `agents_tables` in `PACKAGE_MANIFEST.json`, then run `--sync-adapters`. Rules must make sense without any optional module installed; link module documents from the routing table, not from rules.
4. **Stay agent-neutral.** Use no tool-specific names or features in policy text. Tool specifics belong in `docs/AGENT_TOOLS.md` and the adapter files, and every adapter only points to, exposes or enforces rules from AGENTS.md.
5. **Keep the core stack-neutral.** Mechanism-specific rules (HTMX, a particular database, host hardening) belong in `profiles/`.
6. **Keep tier sizing proportional.** A new gate needs a default in the PROJECT_PROFILE tier table, and a phase in the TESTING_SPEC development-and-release gates.
7. **Every rule that makes agents produce output says where it goes and how it stays bounded.** A rule that adds a record, report, script or deployment step names its home, whether it is overwritten or appended, and its limit. *Why: without that, guidance makes agents write more on every change, and the documents grow until the current state is buried, as happened in one private project's adoption.*

## Workflow for a change
1. Edit the source files. For skills, edit `docs/procedures/<name>.md`, never `.agents/skills/` or `.claude/skills/`.
2. For a new packaged file, add an entry with its `kind`, its `module` (and `stage` if relevant) to `PACKAGE_MANIFEST.json`. Repository-only files go under `repo_only`. Update `maintainer/test_install.py`'s policy if the file changes what a tier installs.
3. Run `python3 check_package.py --sync-adapters --update-manifest`, then `python3 check_package.py`. Both must pass.
4. Run the affected scenarios in [maintainer/SCENARIOS.md](maintainer/SCENARIOS.md) with at least one agent, and preferably with every supported agent for changes to AGENTS.md or the adapters. `python3 maintainer/run_scenario.py <ID> <dir>` builds each fixture, and `maintainer/harness/` runs and scores them automatically ([automated runs](maintainer/SCENARIOS.md#automated-runs)). Record runs in [maintainer/RESULTS.md](maintainer/RESULTS.md). If a change alters the files or profile fields a scenario depends on, update `maintainer/scenarios.json` or the fixture in the same change; `check_package.py` fails until the fixtures build again.
5. Add a log entry below.
