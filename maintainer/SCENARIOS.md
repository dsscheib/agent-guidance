# Guidance scenarios

Repository-only. Use these to test whether agents actually follow the guidance after a change.

## How fixtures are defined
- [`scenarios.json`](scenarios.json) is the single source for every scenario. Each one lists its fixtures, setup patches applied before the initial commit, `dirty` changes left uncommitted, the expected profile and test state, the prompt, and the pass criteria.
- `fixtures/<name>/fixture.json` describes a fixture and supplies the PROJECT_PROFILE.md values it adopts. `fixtures/<name>/files/` holds the files it copies over a fresh install.
- Fixtures are layered in the order listed: an application fixture (`python-cli`, `orders-lib`, `web-app`, `users-db`) supplies the code and project values; a policy fixture (`policy-*`) supplies the owner, tier and git policy; feature fixtures (`nested-service`) add files.
- Fixtures fill placeholders by name, so they keep working as PROJECT_PROFILE.md evolves. A fixture key that matches no placeholder is an error.
- `"install": false` builds an existing project without the package. Profile filling is skipped, and the runner fails if any package file is present. S11 uses this, with the `legacy-docs` fixture, to test the [upgrade procedure](../docs/procedures/upgrade-guidance.md).
- `followups` makes a scenario longitudinal: after the first prompt, paste each follow-up into the same session once the agent finishes the previous step. S12 uses this to test whether documents, deployments and scripts stay bounded across many small changes, which a single prompt cannot show.
- `"remote": true` adds a local bare repository as `origin` inside the fixture's `.git` and pushes the initial commit, so a scenario can test an authorized push without a network.
- `--scenarios FILE` builds another scenario set, with its fixtures in a `fixtures/` folder beside FILE, such as a private holdout set kept outside this repository. `--check` then builds that set and skips the catalog.
- `{guidance}` in a prompt is replaced with this checkout's absolute path when the runner prints it. The agent under test needs read access to that path.

## Running a scenario
1. Build the fixture into a new or empty directory outside this repository:

   ```sh
   python3 maintainer/run_scenario.py S2 ~/scenarios/s2-codex
   ```

   The runner installs the package, layers the fixtures, fills the profile, applies setup patches, makes the initial commit as "Scenario Fixture", and applies any uncommitted changes. It then confirms the profile and test state match the definition, and prints the prompt and pass criteria. `--list` shows all scenarios.
2. Open that directory in the agent under test (Codex, Antigravity, Claude Code, Copilot CLI) and start a fresh session. Paste the prompt verbatim and give no other hints.
3. Compare the agent's behavior with "Expected" and "Must not". Record the agent, its version, the date, the run number and the result in [RESULTS.md](RESULTS.md); the runner prints a row to fill in.

A scenario passes only if every "Expected" item happens and no "Must not" item does. Run each scenario at least twice per agent, in fresh fixture directories, because one pass may be luck.

The fixtures never contain real credentials or reachable hosts; S5's setup URL uses the reserved `.invalid` domain.

## Automated runs
`maintainer/harness/` runs scenarios against agent CLIs in print mode and scores the results. It needs Linux with bubblewrap (`bwrap`) and the agent CLIs, signed in.

```sh
# Run S2 and S12 twice each on two agents; results go outside the repository.
python3 maintainer/harness/run.py --out ~/scenario-runs/2026-11-10 \
    --agents claude@claude-haiku-5-5,copilot@gemini-3.8-flash --scenarios S2,S12

# No-guidance baseline (S1 and S11 are skipped), and a run against another snapshot.
python3 maintainer/harness/run.py --out ~/scenario-runs/2026-11-10 --agents claude --label claude-none --no-install
python3 maintainer/harness/run.py --out ~/scenario-runs/2026-11-10 --agents claude --label claude-main --guidance <snapshot>

python3 maintainer/harness/score.py --out ~/scenario-runs/2026-11-10 --detail   # summary and failure reasons
python3 maintainer/harness/score.py --out ~/scenario-runs/2026-11-10 --digest   # replies, for manual grading
python3 maintainer/harness/score.py --out ~/scenario-runs/2026-11-10 --rows     # rows for RESULTS.md
```

- **Agents** are `claude`, `codex`, `copilot` and `agy`, optionally with a model as `cli@model`. Follow-up prompts (S12) resume the same session.
- **Snapshot.** By default `run.py` copies this checkout, including uncommitted changes, to a committed snapshot under `--out`, because the upgrade procedure in S11 expects a clean guidance checkout. `--guidance` uses another committed snapshot, for example one of `main`.
- **Sandbox.** `sandbox.sh` makes the whole filesystem read-only except the fixture, the log folder and the agent CLIs' own config folders, and gives each run a private `/tmp`. It clears the environment except a short allowlist and hides `~/.ssh` and `/run/user`; `run.py` passes the session bus, and with it the keyring, only to Copilot and Antigravity, which sign in through it.
- **Results** stay outside the repository (`--out` must be elsewhere): they are bulky and contain local paths. A run interrupted by a usage limit is left incomplete and is picked up by the next invocation.
- **Automatic scores** apply one set of core criteria to every configuration, including runs without guidance, so they can be compared. They approximate the Expected and Must not lists and can disagree with a careful reading; record a manual grade instead where they do. Guidance bookkeeping, such as matrix rows and completion-state lines, is reported as metrics, not scored.
- **Authorized actions (S19–S23).** A scenario's `authorized` field names the action the prompt permits (push, merge, deploy or commit). The scorer reports each run's action as *done*; *blocked*, when the agent attempted it and a tool permission or the environment refused it (the guidance's own guardrails ask before `git push`, so in print mode a guided push is usually blocked); or *missed*, when it never attempted it, usually because it stopped to ask again. A miss is a calibration miss: it is counted in its own column and never fails the core verdict, so over-caution shows without being scored as a rule violation. S14 and S23 keep the opposite direction: a stricter role policy holds even when the requester says to go ahead.

Known CLI behavior that affects results:
- **Copilot CLI:** `--trust-folder` cannot be combined with `--resume`, and trust is not saved. The harness sets `COPILOT_ALLOW_ALL=true` instead, which trusts the fixture and loads its hooks on every step, including resumed ones. With Gemini models Copilot prints each tool's full output to stdout, so replies are read from the session export. That export is cumulative across a resumed session; the scorer counts only commands new to each step.
- **Codex:** `--sandbox workspace-write` makes `.git` read-only; the harness adds the fixture's `.git` as a writable root.
- **Antigravity:** has its own command sandbox even with `--dangerously-skip-permissions`, which sometimes blocks `git commit` and `git checkout -b`. It also keeps cross-conversation summaries, which can leak guidance vocabulary into no-guidance runs. For baselines, run with `HOME` pointing at a clean copy of the profile: `~/.gemini/config` plus `antigravity-cli/{bin,builtin,cache,updater,settings.json,installation_id,jetski_state.pbtxt,last_check.timestamp}`, and none of its `conversations`, `brain`, `implicit`, `annotations` or summary files. Add `.gitconfig` so agents can commit, empty the memory folders between batches, and delete the copy afterwards, because it contains sign-in state.
- **Print mode** cannot answer an agent's questions, so criteria that follow an owner answer (S1's implementation, S11's disposition table when the agent stops to ask) cannot be reached.

## Changing scenarios
1. Edit `scenarios.json` or a fixture.
2. Run `python3 maintainer/run_scenario.py --write-table` to regenerate the catalog below.
3. Run `python3 check_package.py`. In template mode it runs `run_scenario.py --check`, which builds every scenario in a temporary directory and fails on a stale catalog, an unmatched patch or profile key, or an unexpected profile or test state.
